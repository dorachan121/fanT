# 06. 未決事項・リスク・前提

## 1. 決定事項（2026-10-24）

| # | 項目 | 決定内容 |
|---|---|---|
| D-01 | コンセプト | 4案（フィルム / キャラ / プリ / AI）を**すべて1つのアプリにモードとして統合**する。フィルム＋美肌を土台にする |
| D-02 | プラットフォーム・技術構成 | **iOS / Android を同時に開発する。TypeScript のモノレポで、役割ごとに技術を組み合わせる**: アプリは Expo（React Native）＋ VisionCamera v5 ＋ react-native-skia、重い処理だけネイティブモジュール（MediaPipe）、社内のフィルムスタジオは React（Web）、サーバーは Firebase（TypeScript）。※当初の「Flutter で両 OS」案から変更（[07](07-system-architecture.md)） |
| D-03 | 課金 | **フリーミアム（年額＋買い切り）**。AI はクレジット制 |
| D-04 | 体制・期間 | **個人開発で、6ヶ月で MVP**（目標は2027年4月末） |
| D-05 | 開発者のスキル | TypeScript / React の経験は5年 |
| D-06 | シェーダーの共通化 | **SkSL（Skia）で1つのソースにする**。アプリのプレビュー・フル解像度での保存・Web のスタジオで同じシェーダーを使う（旧 Q-03 を解決） |

## 3. リスク

| # | リスク | 影響 | 確率 | 対策 |
|---|---|---|---|---|
| R-01 | **スコープ過多**（1人・6ヶ月・4モード・両 OS） | 大 | 高 | MVP のキャラ・プリ・AI はライト版に限定する。「MVP目標（T）」はいつでも削れるようにする。M1 の終わりに再見積もりする。下の「スコープを削る順番」を守る |
| R-02 | Skia の加工と顔検出を同時に動かしたときの性能不足（「フレームレートが落ちる」という報告がある） | 大 | 中 | M1 の PoC（P-1）を最優先する。特徴点の処理は低解像度にして間引く。美肌はネイティブに移せる設計にしておく。それでも足りなければ、Android 版は品質を下げて出すか、後から出す |
| R-03 | iOS・Android・Web の画質の差（色・質感がそろわない） | 中 | 中 | シェーダーは1つのソース（D-06）。ゴールデン画像による比較テスト（P-4） |
| R-04 | 美肌の品質が競合に及ばない | 大 | 中 | 「自然盛り」に振り切る（強い補正では戦わない）。必要なら商用 SDK を検討する（費用対効果を見て） |
| R-05 | AI の原価超過・不正利用 | 中 | 中 | クレジット残高のサーバー管理、App Check、レート制限、上限アラート |
| R-06 | AI の不適切な生成・炎上 | 大 | 低〜中 | モデレーション、本人の写真に限る規約、通報機能、特定の作家の画風は使わない |
| R-07 | 流行の終わり（平成レトロ・キャラブームの終息） | 中 | 低〜中 | コンテンツをデータとして配信する基盤で、すばやく入れ替えられるようにする。4モードで流行を分散させる |
| R-08 | 素材の制作が追いつかない | 中 | 高 | MVP の素材数を最小限にする（フィルム8、キャラ3〜5、台紙4〜6、スタンプ30程度）。Web のフィルムスタジオ（STU）で、アプリと同じ見た目を確認しながら効率よく作る。素材サイトや外注も使う |
| R-09 | ストア審査での差し戻し（課金表示・プライバシー・AI） | 中 | 中 | ガイドラインのチェックリストを用意する。M6 の早い時期に申請する |
| R-10 | 知的財産の侵害（キャラデザイン・カメラ名・フォント） | 大 | 低 | オリジナルデザイン、一般的な名前（「使い捨てカメラ風」など）、ライセンスの確認 |
| R-11 | VisionCamera v5 が新しい（2026年に作り直されたばかり）ことによる不具合・破壊的変更 | 中 | 中 | バージョンを固定する。外部ライブラリの API は `engine/` に閉じ込めて、影響範囲を限定する。PoC で安定性を確認する（P-5） |
| R-12 | Skia で描いた加工がカメラの撮影画像に乗らない | 中 | 確定 | 元の写真を撮ってから、同じシェーダーを画面外でかけ直す。乱数シードを記録して、プレビューと一致させる（[07](07-system-architecture.md) §5.2） |
| R-13 | ネイティブモジュール（Swift / Kotlin）開発の経験不足 | 中 | 中 | ネイティブの範囲を MediaPipe の薄いラッパーに限定する。公式サンプルと既存のプラグインを参考にする。M1 で最初に着手する |

## 4. スコープを削る順番（遅れた場合）

スケジュールが遅れたら、上から順に Phase 2 に回します。

1. AI-08 期間限定スタイル / AI-06 AI 生成の表示（目に見えるマークだけ残す）
2. PRI-04 背景の合成
3. CHR-05 キャラの複数人対応 / BTY-05 美肌の複数人対応
4. SHR-03 Instagram ストーリーズへの直接共有（OS の共有シートで代用）
5. CNT-03 / CNT-04 NEW バッジ・期間限定の配信
6. BTY-04 顔の微調整
7. PRI-08 推し活フレーム / FLM-07 フレーム
8. **それでも足りない場合**: AI モードを丸ごと MVP から外し、リリース後1〜2ヶ月で追加する（原価がかかり、運用リスクも最大の機能のため）

## 5. 前提

- 開発者は TypeScript / React の経験が5年ある。ネイティブ（Swift / Kotlin）は、MediaPipe のラッパー程度を学びながら実装する
- Apple Developer Program と Google Play Console に登録する（年額 / 登録料が発生）
- クラウドの費用は、MVP の期間は月数千円以内に収まる想定（AI の生成費用は除く）
- 市場調査の数値は公開情報にもとづく推計で、インタビューと実データで検証していく
